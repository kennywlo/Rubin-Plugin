# Stage example workloads

Three example CGSim workload files, in the same `jobs[]` schema as
`../real_quantum_graph.json`, generated by `generate_stage_examples.py`:

- `example_stage1_single_visit.json` — 340 jobs
- `example_stage2_recalibrate.json` — 275 jobs
- `example_stage3_coadd.json` — 276 jobs

## Why these exist

`../real_quantum_graph.json` is confirmed RC2/HSC-derived (`data_id.instrument:
"HSC"`), not from the actual LSSTCam DRP1 pipeline — see
`CGSim/LLM-Interface/docs/rubin_plugin_quantum_graph_pipeline_mismatch` context
in memory, or cross-check its task labels against
`~/llm-apps/app/rubin_drp_pipeline/pipeline_drp_pipe_LSSTCam_DRP.yaml` directly.

These three files instead take their task list and dependency shape straight from
the real `DRP.yaml` pipetask build reports (`pipeline_drp_pipe_LSSTCam_DRP_stage{1,2,3}-*.pdf`
in `~/llm-apps/app/rubin_drp_pipeline/`), so they use `instrument: "LSSTCam"` and
real task labels (`finalizeCharacterizationDetector`, `fgcmFitCycle`,
`assembleDeepCoadd`, `forcedPhotCoadd`, ...) with fan-in shapes that match the
actual pipeline (detector→visit, visit→tract, visit→patch→tract).

They deliberately **exclude** the parallel QA/analysis-tools branch of each stage
(metric tables, whole-sky plots, fgcm diagnostic plots) — those fan out to dozens
of near-zero-cost tasks per stage that don't meaningfully change scheduling load,
only diagram complexity.

## What is and isn't real here

- **Real:** task labels, dependency/fan-in structure, `instrument` value, and the
  general shape of `flops`/`cores` (cores mostly 1, matching the real corecount
  distribution measured from `panda_prod_test` OpenSearch data across all 4 Rubin
  PanDA facilities; a few global/heavy-fan-in tasks bumped to multi-core to match
  that data's max-corecount tail).
- **Assumed, not measured:** the campaign scale (2 tracts × 4 patches × 6
  visits/tract × 9 detectors × 3 bands) is a readable stand-in sized for an
  example, not DRP1 scale. Per-task `flops` are order-of-magnitude guesses except
  `isr` and `calibrateImage`, which reuse `real_quantum_graph.json`'s measured
  averages since those two task types are common to both graphs.
  `gbdesHealpix3AstrometricFit` is modeled per-tract as a stand-in for the real
  healpix3 pixelization, which this generator doesn't implement.

Each stage file is self-contained: inputs that would actually come from a prior
stage (or from calibs/skymap) are registered as pre-existing external files
available at `creation_time: 0`, the same pattern
`../../rubin-data/generate_campaign.py` uses for raw inputs.

## Regenerating

```
python3 generate_stage_examples.py
```

Deterministic — no randomness, so reruns produce identical output.
