# Stage example workloads

Four example CGSim workload files, in the same `jobs[]` schema as
`../real_quantum_graph.json`, generated by `generate_stage_examples.py`:

- `example_stage1_single_visit.json` — 344 jobs
- `example_stage2_recalibrate.json` — 307 jobs
- `example_stage3_coadd.json` — 375 jobs
- `example_stage4_variability.json` — 476 jobs

1,502 jobs total, 0 bad parent references, 0 bad child back-references, 0
orphaned non-t0 jobs (validated after every regeneration — see "Regenerating"
below).

## Why these exist

`../real_quantum_graph.json` is confirmed RC2/HSC-derived (`data_id.instrument:
"HSC"`), not from the actual LSSTCam DRP1 pipeline — see
`CGSim/LLM-Interface/docs/rubin_plugin_quantum_graph_pipeline_mismatch` context
in memory, or cross-check its task labels against
`~/llm-apps/app/rubin_drp_pipeline/pipeline_drp_pipe_LSSTCam_DRP.yaml` directly.

These four files instead take their task list and dependency shape straight from
the real `DRP.yaml` pipetask build reports in `~/llm-apps/app/rubin_drp_pipeline/`
(`pipeline_drp_pipe_LSSTCam_DRP_stage{1,2,3}-*.pdf` for the aggregate view, plus
every `step1*`/`step2*`/`step3*`/`step4*-*.pdf` sub-diagram — all 20 PDFs in that
directory have now been read), so they use `instrument: "LSSTCam"` and real task
labels (`finalizeCharacterizationDetector`, `fgcmFitCycle`, `assembleDeepCoadd`,
`forcedPhotCoadd`, `makeRGBPicturePrettyCoaddGRI`, ...) with fan-in shapes that
match the actual pipeline (detector→visit, visit→tract, visit→patch→tract,
patch→healpix8→healpix3→allsky).

**Unlike the first version of this generator, the QA/analysis-tools branch is now
included** for all 4 stages — metric tables, whole-sky plots, fgcm diagnostic
plots, property maps, RGB "pretty picture" coadds, and HiPS tile generation are
all modeled as real task nodes with real dependencies, not excluded. A QA task is
modeled as **one job per task invocation** (matching the real pipeline's
granularity), with that task's many named plot/metric datasets bundled into a
couple of representative `output_files` entries rather than exploded
one-job-per-dataset-name — a real `makeAnalysisSingleVisitStarAssociationWholeSkyPlot`
invocation produces ~22 plot datasets in ONE task run, not 22 separate jobs.

### Stage 4

Stage 4 (`step4b`–`step4f` in the source PDFs) is new in this revision: solar-system
ephemerides generation, DIA/variability source association, forced photometry on
detector-level difference/visit images, the "pretty picture" RGB coadd pipeline,
and HiPS tiles from those RGB images. There is no aggregate "stage4" PDF the way
there is for stages 1–3 — `WHERE_IS_STEP4A_OR_STAGE4.html` is a redirect stub, and
there is no `step4a` at all — so this file was assembled directly from `step4b`
through `step4f`, each read individually.

## What is and isn't real here

- **Real:** task labels, dependency/fan-in structure, `instrument` value, and the
  general shape of `flops`/`cores` (cores mostly 1, matching the real corecount
  distribution measured from `panda_prod_test` OpenSearch data across all 4 Rubin
  PanDA facilities; a few global/heavy-fan-in tasks bumped to multi-core to match
  that data's max-corecount tail).
- **Assumed, not measured:** the campaign scale (2 tracts × 4 patches × 6
  visits/tract × 9 detectors × 3 bands) is a readable stand-in sized for an
  example, not DRP1 scale. Per-task `flops` are order-of-magnitude guesses except
  `isr` and `calibrateImage`, which reuse `real_quantum_graph.json`'s measured
  averages since those two task types are common to both graphs. QA/plot-producing
  tasks are given deliberately low `flops` relative to compute tasks, since they
  aggregate/plot existing data rather than reprocess images.
  `gbdesHealpix3AstrometricFit`, and the stage3/stage4 HiPS tasks
  (`makeHighOrderHips*`/`makeLowOrderHips*`), are modeled per-tract or per-band as
  a stand-in for the real healpix3/healpix8 pixelization, which this generator
  does not implement pixel-accurately.
- **Scope limits, documented rather than silently dropped:** template-coadd QA (a
  near-duplicate of deep-coadd QA in step3a/3b) is not modeled, to avoid doubling
  an already-large QA branch with structurally identical tasks. Stage 4's forced-
  photometry and DIA-source tasks assume `difference_image`/`visit_image` already
  exist (produced by AP/prompt processing, which no stage here models) and treat
  them as external `creation_time: 0` inputs. Step3c's 6 real per-band
  `makeSingleBandRGBCoadd{Z,Y,U,R,I,G}` tasks are collapsed into one
  `makeSingleBandRGBCoadd` job per patch covering this generator's 3 configured
  bands, to avoid inflating job count for bands (u, z, y) this generator doesn't
  otherwise model.

Each stage file is self-contained: inputs that would actually come from a prior
stage (or from calibs/skymap) are registered as pre-existing external files
available at `creation_time: 0`, the same pattern
`../../rubin-data/generate_campaign.py` uses for raw inputs.

## Regenerating

```
python3 generate_stage_examples.py
```

Deterministic — no randomness, so reruns produce identical output. After
regenerating, validate structurally:

```python
import json
for fn in ["example_stage1_single_visit.json", "example_stage2_recalibrate.json",
           "example_stage3_coadd.json", "example_stage4_variability.json"]:
    d = json.load(open(fn))
    jobs = {j["jobid"]: j for j in d["jobs"]}
    assert all(p in jobs for j in d["jobs"] for p in j["parents"])
    parent_of = {j["jobid"]: set(j["parents"]) for j in d["jobs"]}
    assert all(j["jobid"] in parent_of.get(c["jobid"], set())
               for j in d["jobs"] for c in j["children"])
    assert all(j["parents"] or j["creation_time"] == 0.0 for j in d["jobs"])
```
